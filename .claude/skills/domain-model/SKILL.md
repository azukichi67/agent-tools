# ドメインモデルによる設計

機能や処理の順番、画面や DB の都合でプログラムを分けると、業務的な判断・加工・計算がサービスクラスや画面のコードに散らばる。業務ルールが1つ変わるたびに、散らばった全ての箇所を探して直すことになる。業務の関心事とクラスを1対1に対応させれば、業務ルールを変えるときに直す場所が、対応するクラスに閉じる。

## このスキルが決める範囲

- 決めるのは、業務の関心事のどれをドメインオブジェクトにするかと、業務ロジックをドメインモデルとアプリケーション層のどちらに置くか。
- 1つのクラスの中の書き方（値オブジェクト・完全コンストラクタ・不変・コレクションオブジェクト・区分ごとの分岐・結合）は `code-design` Skill（`.claude/skills/code-design/SKILL.md`）に従う。本スキルの「クラス」の意味も `code-design` の適用範囲と同じ。
- 識別子の英語の形は `code-naming`、テーブルの定義は `db-definition` に従う。

## 設計の手順

1. **業務の言葉を集める。** 要件と業務フロー（業務の活動を時間軸に沿って並べ、活動の主体ごとに情報のやりとりを書いたもの）から、業務で使われている名詞と動詞を書き出す。業務フローの全ての活動について、登場するものを書き出したら終わり。
2. **ヒト・モノ・コトに分ける。** 手順1の言葉を分け、コトごとに関わるヒトとモノを結びつける（規則2）。全ての言葉がどれかに分かれたら終わり。
3. **業務ルールを書き出す。** コトごとに、起きてよいこと・起きてはいけないことと、想定外のことが起きたときの対応を書く（規則3）。状態を持つコトは状態遷移図を描く（規則4）。分からないルールはユーザーに確かめる。全てのコトにルールが書かれたら終わり。
4. **ドメインオブジェクトを決める。** 関心事ごとに、データとそのデータを使う判断・加工・計算を1つのクラスにまとめる（規則1・5）。手順3の全てのルールに置き場所のクラスが決まったら終わり。
5. **アプリケーション層を決める。** 画面や外部からの要求ごとに、サービスクラスのメソッドが何をどの順で呼ぶかを決める（規則6〜8）。全ての要求について、呼ぶ順番と約束事が決まったら終わり。
6. 「書き終えたら確かめること」を全て満たすまで直す。

ヒト・モノ・コトの分け方や、サービスクラスの良い例と悪い例が要るときは `references/examples.md` を参照する。

## 規則

### 1. 業務で使われている言葉をそのままクラスにする

**症状:** 業務の人が使わない、抽象的で意味の広い言葉をクラス名やパッケージ名にしている。広い範囲をまとめられたように見えるが、何を表すクラスかは名前から分からない。

**直し方:** 業務の人が普段使っている言葉を、そのままクラス名・メソッド名にする。同じものを指す言葉が業務の中で複数あるときや、言葉の意味が曖昧なときは、どれを使うかをユーザーに確かめる。

**なぜ:** 仕様変更の依頼は業務の言葉で来る。名前が業務の言葉と一致していれば、依頼の言葉から直す場所を探せる。

### 2. コトを軸に関心事を整理する

**症状:** テーブルや画面の項目から考え始め、データの置き場所だけが決まって、業務ロジックの置き場所が決まらない。

**直し方:**

- 業務の関心事を、ヒト（顧客・担当者・取引先）・モノ（商品・設備）・コト（受注・出荷・請求・入金のような業務の出来事）に分ける。
- コトを中心に置き、そのコトに関わるヒトとモノを結びつける。
- データの整理ではなく、業務ロジックの整理として行う。

**なぜ:** 業務ルールの多くは、コトが起きてよいかの判断と、コトに伴う計算である。コトを軸にすると、業務ロジックの置き場所が決まる。

### 3. 業務ルールを、起きてよいこと・起きてはいけないことの判断として書く

**症状:** 「注文を取り消せるか」のような判断が、画面やサービスクラスの if 文に埋もれている。想定外のこと（取り消し・返品・訂正など）への対応が決まっておらず、起きてから場当たりで直す。

**直し方:**

- コトごとに、起きてよいこと・起きてはいけないことの判断を、そのコトのドメインオブジェクトのメソッドにする。
- 業務では必ず想定外のことが起きる。どう対応するかの原則を業務の人（ユーザー）に確かめ、それも業務ルールとして書く。

**なぜ:** 判断がドメインオブジェクトの1か所にあれば、ルールが変わったときに直す場所が1つで済む。

### 4. 状態遷移図と列挙型を対応させる

**症状:** 状態の名前と、どの状態からどの状態に移れるかが、コードのあちこちの条件分岐から読み取るしかない。

**直し方:** 状態を持つコトは、状態遷移図を描いてから設計する。図の状態を列挙型（TypeScript では union 型）の値に、遷移をドメインオブジェクトのメソッドに1対1で対応させる。分岐の書き方は `code-design` の規則5に従う。

**なぜ:** 分析で描いた図とコードが1対1に対応していれば、業務の人と図で確かめた内容を、そのままコードで確かめられる。

### 5. ドメインオブジェクトを、機能・処理の順番・画面・DB から独立させる

**症状:** ドメインオブジェクトが、どの画面のどの処理の何番目に呼ばれるかを前提にしている。画面の表示用の整形や、SQL・ORM の都合を持っている。

**直し方:** 特定の業務のデータと、そのデータを使う判断・加工・計算だけを切り出す。どの機能のどこで使われるかが決まっていなくても設計でき、単体で動作を確かめられる部品にする。例えば消費税クラスは、税率と税額の計算・端数の丸めだけを持つ。

**なぜ:** 機能の分解構造や処理の前後関係に依存した部品は、機能や順番が変わると一緒に直すことになる。オブジェクトとテーブルは設計の動機が違うので、同じ形に揃えると片方の都合でもう片方が歪む。

### 6. 業務ロジックをサービスクラスに書かない

**症状:** サービスクラスが、ドメインオブジェクトからデータを取り出して判断・加工・計算している。サービスクラスが関心事の交差点になり、長く複雑になる。

**直し方:** サービスクラスは業務処理の進行役・調整役にする。ドメインオブジェクトを用意し、判断・加工・計算をドメインオブジェクトに任せ、結果を保存する順番を決めることだけをする。使う側のクラスにロジックを書き始めたら、そのロジックをデータを持つドメインオブジェクトに移す。

**なぜ:** サービスクラスで判断すると、同じ判断が別のサービスクラスに複製され、業務ルールの変更が1か所で済まなくなる。

### 7. 画面とデータベースの都合をサービスクラスに持ち込まない

**症状:** 1つの画面の操作に合わせて、関心事の違う処理を1つのメソッドに詰め込んでいる。サービスクラスに SQL やテーブルの構造の知識がある。

**直し方:**

- サービスクラスのメソッドは、業務の基本処理の単位に分ける。画面が複数の処理を一度に求めるときは、基本処理を組み合わせた複合サービスを別に用意する。
- データベースの読み書きは、サービスクラスから見えない場所（リポジトリなど）に分けて隠す。

**なぜ:** 画面や DB の都合は業務ルールとは別のきっかけで変わる。混ぜると、画面の変更が業務処理を壊す。

### 8. サービスクラスと使う側の約束事を決める

**症状:** 使う側が、サービスクラスが何を受け付けて、どんなときに失敗するかを、中身を読まないと判断できない。

**直し方:**

- null を渡さない・返さない（`code-design` の規則8）。
- 状態によって実行できない操作は、使う側が先に実行できるかを確かめられるようにする（「取り消せるか」を問い合わせてから「取り消す」）。
- 約束を守って呼ばれたのに起きた異常は、例外で知らせる。

**なぜ:** 約束事が決まっていれば、使う側もサービスクラスも、約束の外の場合を検査するコードを持たずに済む。

## 書き終えたら確かめること

- [ ] 1. クラス名・メソッド名が、業務の人が使っている言葉になっているか
- [ ] 2. 業務の関心事がヒト・モノ・コトに分かれ、コトごとに関わるヒトとモノが決まっているか
- [ ] 3. 起きてよいこと・起きてはいけないことの判断が、コトのドメインオブジェクトに置かれ、想定外のことへの対応が決まっているか
- [ ] 4. 状態を持つコトの状態と遷移が、列挙型の値とメソッドに1対1で対応しているか
- [ ] 5. ドメインオブジェクトが、呼ばれる機能・順番・画面の表示・DB の構造を前提にしていないか
- [ ] 6. サービスクラスに、業務的な判断・加工・計算が書かれていないか
- [ ] 7. サービスクラスのメソッドが業務の基本処理の単位になり、DB の読み書きが隠されているか
- [ ] 8. 状態によって実行できない操作を、使う側が先に確かめられるか
