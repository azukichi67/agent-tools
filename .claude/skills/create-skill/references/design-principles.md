# スキルの設計原則

スキルは、エージェントが毎回同じ手順を踏むための文書である。ソフトウェア設計の原則（単一責任・関心の分離・依存性逆転）が、そのまま当てはまる。

## 1. 責務を1つにする

1つのスキルには1つの目的だけを持たせる。目的の単位は、「〜と〜」で繋がずに1文で書けること。

いくつもの責務を抱えたスキル（神スキル）は、使うたびに「この手順はやらないで」と指示を足すことになる。例えば「PR を作る」スキルが lint・テスト・コミット・push・PR 作成を全て抱えていると、コミットだけ済ませたいときに使えない。

スキル以外の仕組みに回すほうがよいものは、切り出して置き場所を提案する。

| 中身 | 置き場所 |
|---|---|
| 毎回必ず、機械的に走らせる処理（lint・テスト・フォーマット） | hooks |
| どの作業でも常に守る規約（コミットの書き方・返答の書き方） | `.claude/rules/` |
| 1つのリポジトリでだけ通じる指示 | そのリポジトリの `CLAUDE.md` |
| 判定のロジック（言い回しで結果が揺れると困るもの） | `scripts/` のスクリプト。スキルには呼び出す手順だけを書く |
| 手順を伴う作業で、使う場面が限られるもの | スキル |

## 2. 振る舞いとナレッジを分ける

スキルの中身は2種類ある。

- **振る舞い**: 何をどの順でするか（手順）。やり方そのものが変わったときに変わる。
- **ナレッジ**: 何を見るか、何を知っているべきか（観点・規約・用語・例）。新しい知見を得たときに変わる。

変わるきっかけが違うので、振る舞いは `SKILL.md` に、ナレッジは `references/*.md` に置く。混ぜると、観点を1つ足すたびに手順の文章を壊さないよう書き直すことになる。コードなら関数に切り出せるが、自然言語の文章ではそれができない。

分けておくと、次のことができる。

- ナレッジだけを足し引きできる。手順に詳しくない人でも、観点やドメイン知識を足せる。
- 同じ振る舞いを、別のナレッジと組み合わせて使い回せる（例: 同じレビュー手順に、バックエンド用・インフラ用の観点ファイルを足す）。
- 振る舞いの変更とナレッジの更新が別々の差分になり、レビューしやすい。

ナレッジのファイルは見出しで分類し、箇条書きにする。観点を足したら、なぜ足したかを日付付きで添える。観点は足すより消すほうが難しく、理由が残っていれば後で消すかどうかを判断できる。

### 分ける前と後

分ける前（手順と観点が1つの文章に混ざっている）:

```markdown
# PR Review

変更箇所を起点にレビューする。

変更だけで問題を判断できない場合は周辺コードも確認し、
既存挙動を壊していないか、名前と実際の意味が一致しているかを確認する。

PR本文に「挙動は変わらない」と書かれている場合は、
条件式や既定値まで確認して、その説明が正しいか検証する。

レビュー中に同じ仕様を変更するために複数箇所の修正が必要だと分かった場合は、
設計上の問題として指摘する。
```

分けた後の `SKILL.md`:

```markdown
# PR Review

変更箇所を起点にレビューする。

変更箇所だけで判断できる場合はそこで完結し、必要な場合のみ周辺コードへ調査を広げる。

レビュー観点の確認が必要な場合は [review-guidelines.md](./references/review-guidelines.md) を参照する。
```

分けた後の `references/review-guidelines.md`:

```markdown
# Review Guidelines

## Semantic correctness

- 名前と実際の意味が一致しているか

## Behavior

- 既存挙動を壊していないか
- PR本文が「挙動は変わらない」としている場合、条件式や既定値まで確認して裏を取る

## Architecture

- 同じ仕様を変更するために複数箇所の修正が必要な設計になっていないか
```

## 3. 必要なときに必要な分だけ読ませる

`references/` への参照は、読む条件を付けて書く。どの場合に読むかが文から分かれば、エージェントは不要なときに読まずに済む。

- 一部の場合にだけ要るもの: 「〜のときは `references/x.md` を参照する」と、条件を具体的に書く。
- 毎回必ず要るもの: 手順の中に「`references/x.md` を読む」という1ステップとして書く。条件付きにすると、要るときに読み飛ばされる。

判断の基準は、スキルが扱う場合（分岐）の全てで要るかどうか。全てで要るものは手順に、一部でだけ要るものは条件付きの参照にする。

## 4. 実装手段ではなく目的を書く

特定のツールやコマンド（例: 「`gh pr view` で差分を取る」）ではなく、目的（「PR の差分を読む」）を書く。手段を書くと、そのツールが無い環境で動かず、ツールを替えるたびに `SKILL.md` を直すことになる。どのツールを使うかはエージェントに任せる。

スキルの目的そのものが特定のツールに依存する場合は、ツール名やコマンドを書いてよい（例: git の操作を細かく決める `create-commit`）。

## 5. エージェントが毎回同じ手順を踏むように書く

- **してほしいことを肯定形で書く。** 「〜しない」と書くと、その行動が文脈に入り、かえって起きやすくなる。肯定形で書けない絶対の禁止だけを否定形にし、そのときも何をすべきかを並べて書く。
- **各手順の終わりに、終わったと判断できる条件を書く。** 「理解する」のように終わりがぼやけた手順は、先の手順に気を取られて早く切り上げられる。「対象の SKILL.md の全ての節について問題の有無を書き出した」のように、確かめられて漏れが無い条件にする。
- **既定の振る舞いを書かない。** 書かなくてもエージェントがそうする指示は、毎回トークンを使って何も変えない。
- **環境を見れば分かることを書き写さない。** ディレクトリの構成、`package.json` のスクリプト、`--help` の出力などは古くなる。書くのは、見ても分からないこと（暗黙の規約・選んだ理由・はまりどころ）だけにする。
- **1つの意味は1か所に書く。** 同じ内容が2か所にあると、片方だけ直されて食い違う。

## 6. description は、いつ使うかを書く

`description` は常に読み込まれていて、エージェントがスキルを使うかどうかを決める唯一の手がかりになる。

- 使う場面を先頭に書く。
- 使う場面が複数あれば、別の場面ごとに1つずつ書く。同じ場面の言い換えは並べない。
- 本文を読めば分かる詳細は書かない。

ユーザーが名前を打って呼ぶだけで、エージェントや他のスキルから呼ばれることが無いスキルは、`disable-model-invocation: true` にする。description が文脈に載らなくなる代わりに、ユーザーがスキルの存在を覚えておく必要がある。

## アンチパターン

| アンチパターン | 起きること | 直し方 |
|---|---|---|
| 神スキル | 使うたびに「これはしないで」と足す | 原則1で分け、hooks・rules に回す |
| 手順の文章に観点を埋め込む | 観点を足すたびに文章を書き直す | 原則2で `references/` に出す |
| 一部でしか要らない参照を毎回読ませる | トークンと注意が無駄になる | 原則3で条件付きの参照にする |
| 特定ツールの決め打ち | ツールが無い環境で動かない | 原則4で目的を書く |
| 古い記述の積み重ね | 生きている指示が埋もれる | 原則5で、今も効いていない行を消す |
