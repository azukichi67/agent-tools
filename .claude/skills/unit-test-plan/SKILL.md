# 単体テストの設計

単体テストの目的は、振る舞いが変わったときにだけ落ち、リファクタリングでは落ちないテストを、必要最小限の数で持つことである。量より質を取る。カバレッジは目標にしない。

## 適用範囲

- テスト名とテスト内のコメントは `code-comments` の「テストコード（What）」、識別子は `code-naming` に従う。テスト名について本スキルが加えるのは規則6と規則8（PBT の性質をテスト名にする）だけである。
- テストは Vitest で書く（設定は `vitest.config.ts`。全テストを jsdom で実行する）。
- テストファイルはリポジトリ直下の `tests/` に、`src/` と同じ構成で置く（`src/places/place-id.ts` → `tests/places/place-id.test.ts`）。`src/` にテストを置かない。テストどうしで共有する部品は `tests/support/` に置く。
- どの種類の不具合を単体テスト（PBT を含む）で検出するかは、`test-layering` Skill（`.claude/skills/test-layering/SKILL.md`）の割り当て表が決める。本スキルは、単体テストの対象・ケース・書き方を扱う。
- E2E テストの書き方は扱わない（`e2e-test-plan` が扱う）。

## 設計の手順

手順1〜4は、実装計画のテスト方針を書く前、またはテストを書き始める前に通す。手順5は、テストを書き終えたあとに行う。

1. **対象を選ぶ。** 単体テストを書くのは、複雑な条件分岐や計算を持つドメインロジックだけにする。ビジネスロジックが薄い処理（単純な CRUD、値の受け渡しだけの処理）は E2E で確かめ、単体テストを書かない（`test-layering` の割り当て表）。画面（React コンポーネント）は例外で、後述の「画面の単体テスト」に従って単体テストを書く。
2. **要件から振る舞いを列挙する。** Issue や `docs/requirements.md` に書かれた要件を、「どういう状態で・何をすると・どうなる」の形の振る舞いに書き直す。コードの分岐を網羅する発想ではなく、要件に書かれた振る舞いを起点にする。
3. **振る舞いごとに検証する場所を1つ決める。** 同じ振る舞いは、それを外に公開している最上位の型（集約など）のテストで1回だけ検証する。集約が使う依存先（値オブジェクトなど）にテストを書くのは、集約のテストでは確かめにくい依存先固有の契約（不変条件、境界値、丸め）だけにする。
4. **テストダブルを使う依存を決める。** 規則3に従う。
5. **実装をわざと壊して、テストが落ちることを確かめる。** テストを書いたエージェントが行う。振る舞いごとに、検証対象の実装を1か所わざと壊し（例: `>=` を `>` にする、返す値を変える）、`pnpm test` でその振る舞いのテストが落ちることを確かめる。落ちなければ、テストを直す。壊した変更は確かめるたびに元に戻し、コミットに含めない。未コミットの実装を消さないよう、`git checkout` ではなく、壊した1か所を手で戻す。

完了条件: 手順2で列挙した振る舞いの全てに、検証する場所が1つずつ割り当たっている。割り当たらない振る舞いがあれば、要件が曖昧なので確認する。手順5で、全ての振る舞いのテストが、壊した実装に対して落ちた。

## 規則

### 1. 「単体」は1つの振る舞いを指す

**症状:** クラスやメソッド1つごとにテストファイルを作り、それ以外の依存を全てモックにしている。

**直し方:** 1つのテストで1つの振る舞いを検証する。その振る舞いに関わるアプリ内部のクラス・関数は、複数あっても本物を組み合わせて使う。隔離するのはテストどうし（実行順や共有状態に依存しない）であり、テスト対象のクラスどうしではない（古典派）。

**なぜ:** クラス単位で隔離すると、テストが内部の分け方に縛られ、クラスの分割や統合のたびにテストを書き直すことになる。

### 2. 出力値と状態変化を検証する

**症状:** 内部メソッドの呼び出し有無・呼び出し回数・引数を検証している。private なメソッドやプロパティを、テストのために公開している。

**直し方:** 検証するのは次のどちらかにする。

- 出力値: Act の戻り値
- 状態変化: Act のあとに、公開された手段で観察できる状態

private なロジックは、それを使う公開された振る舞いのテストを通して確かめる。

**なぜ:** 呼び出しの手順は実装の詳細であり、振る舞いが同じでもリファクタリングで変わる。手順を検証するテストは、正しいコードに対して落ちる（偽陽性）。

### 3. テストダブルは、管理外の依存にだけ使う

**症状:** アプリ内部の協調オブジェクトをモックにしている。スタブが呼ばれたことを検証している。テストが壊れたあと、通すために依存をモックに置き換えている。

**直し方:**

- テストダブルに置き換えるのは、テストの外から観察される副作用を持ち、アプリが管理していない依存だけにする（外部 API、メール送信、メッセージの送信先など）。
- アプリ内部のクラス・関数は本物を使う。
- 時刻・乱数のように結果を不安定にする入力は、引数として外から渡す。
- 置き換えた依存が値を返すだけ（スタブ）なら、呼び出しは検証せず、その値を使った結果だけを検証する。外へ送る副作用（モック）なら、送った内容を検証する。

**なぜ:** 管理外の依存への送信はシステムの外から見える振る舞いなので、検証する価値がある。内部の協調は実装の詳細なので、規則2と同じく偽陽性の原因になる。

### 4. AAA パターンで書く

**症状:** 準備・実行・検証が入り混じる。1つのテストで実行と検証を何度も繰り返す。テスト内に if や for がある。

**直し方:**

- テスト本体を Arrange（準備）・Act（実行）・Assert（検証）の3つに分け、`// Arrange` `// Act` `// Assert` のコメントで区切る。
- Act はテスト対象の呼び出し1文にする。1つの振る舞いに複数の呼び出しが要るなら、公開 API がその振る舞いを1回の呼び出しで提供できていない兆候なので、API の設計を見直す。
- 1つのテストに Arrange・Act・Assert を1組だけ置く。2つ目の実行が必要なら、別のテストに分ける。
- テスト本体は分岐・ループの無い直線のコードにする。入力違いは規則5の `it.each` に移す。
- Arrange が長い、または複数のテストで重複するなら、テスト対象を組み立てる関数（ファクトリ関数）に切り出し、各テストの Arrange で呼ぶ。`beforeEach` で共有の状態を作らない。
- Assert は、その振る舞いの結果を1文で言える範囲に絞る。同じ振る舞いの結果（戻り値と状態変化など）なら、複数の `expect` を並べてよい。

**なぜ:** 構造が揃っていると、読み手はどこが準備でどこが検証かを探さずに読める。共有の準備は、テストどうしを結合させ、1つのテストを読むのに別の場所を追わせる。

### 5. 入力違いは `it.each` にまとめる

**症状:** 入力と期待値だけが違うテストを、コピーして並べている。

**直し方:** 同じ振る舞いの入力違いは `it.each` にまとめる。テーブルの各行に、入力（Arrange に使う値）と期待値（Assert に使う値）を並べる。テスト名は各行ごとに `$` 記法で具体的な値を埋める。

**なぜ:** ケースの追加がテーブルへの1行の追加で済み、テスト本体の重複がなくなる。

**適用しない場合:** 行ごとに Arrange の手順や Assert の対象が変わるなら、別の振る舞いなのでテストを分ける。テーブルにフラグ列を足して手順を切り替えない。

### 6. テスト名に業務上の意味を書く

**症状:** テスト名が `calculate returns 1100` のように、メソッド名と戻り値の説明になっている。

**直し方:** テスト名は日本語で、業務上の意味を書く（例: 「在庫不足の場合は購入失敗し在庫は変わらない」）。テスト名にメソッド名・クラス名を含めない。`describe` には、メソッド名ではなく機能の名前を書く。

**なぜ:** メソッド名を入れると、名前の変更というリファクタリングでテスト名が嘘になる。業務の言葉で書けば、開発者以外もテスト名から仕様を読める。

### 7. テストが壊れたら、原因を切り分けてから直す

**症状:** テストが落ちたとき、原因を特定せずに期待値を書き換える、または依存をモックに置き換えて通している。

**直し方:** 先に、落ちた原因が次のどちらかを切り分ける。

- 振る舞いが変わった: 要件どおりの変更ならテストの期待値を直す。要件にない変更なら、実装のバグとして直す。
- 振る舞いは同じだが落ちた: テストが実装の詳細に依存している。規則2・3に従って、出力値と状態変化を検証する形に書き直す。

原因が切り分けられないときは、推測で直さずユーザーに確認する。

**なぜ:** 通すことを目的にモックへ置き換えると、テストが実装の手順を検証する形に偏り、次のリファクタリングでまた壊れる。

### 8. 入力は、型が有限なら全て列挙し、範囲が広ければ PBT で性質を検証する

**症状:** 境界値をいくつか手で選んで並べ、選ばなかった入力が正しいかは確かめていない。取りうる値が有限なのに、組み合わせの一部だけを並べている。

**直し方:**

- 引数が、取りうる値が有限の型（union、`as const` の列挙）だけでできた関数は、全ての組み合わせを `it.each` で列挙する（規則5）。
- 範囲の広い型（任意の整数・文字列など）を受け取る関数は、PBT で性質を検証する。性質は「どの金額を足しても、合計は0以上」のように1文で書き、テスト名にする。
- `test-layering` で PBT に割り当てた状態遷移の組み合わせとドメインの不変条件は、操作の列を生成し、どの順で操作しても不変条件が保たれることを性質として検証する。
- PBT は fast-check で書く。未導入なら、最初に PBT が必要になった実装で devDependencies に追加する。書き方は、そのとき導入したバージョンの公式ドキュメントで確かめる。
- 生成器は、値の生成関数（brand 型のパース関数。`code-design` 規則4）を通して作る。正しい値だけが生成され、不正な入力による誤報が起きない。

**なぜ:** 手で選んだ入力では、選ばなかった入力の誤りを検出できない。全てを列挙するか、性質を全ての入力について検証すれば、人がレビューするのは個々のテストではなく、入力の型の定義と、テストが確かめる性質の1文だけになる。

## 画面の単体テスト

画面（`src/routes/**`）の単体テストは、ルートから切り出した描画用のコンポーネントを、props でデータを渡して描画して確かめる。

- **確かめること:** props で渡したデータの見え方と、フォームの操作に対する表示とコールバックの呼ばれ方だけにする。loader・notFound の判定・画面の遷移・toast・ログインは E2E で確かめる。並び順や検証ルールの細部など、純粋関数のテストで確かめ済みのことは繰り返さない。
- **E2E の書き方:** `e2e-test-plan` Skill（`.claude/skills/e2e-test-plan/SKILL.md`）に従う。
- **切り出し方:** 描画部分はルートフォルダ内の `-components/` に置く（`-` で始まるファイルとフォルダはルートツリーから除外される）。ルートには loader・search の解析・server function の呼び出し・遷移を残し、コンポーネントには結果だけを props で渡す。コンポーネントは `*.functions.ts` と `*.server.ts` を import しない。テストの import が `cloudflare:workers` に届いて落ちたら、stub で回避せず、コンポーネントの import を直す。
- **props で注入するもの:** loader の結果（表示用データ。変換関数を通さずテストで直接作る）、search から求めた値、保存などの処理（`onSubmit` のような Promise を返すコールバック）。
- **テストダブル:** props のコールバックだけを `vi.fn` にする。コンポーネントの外へ出る出力なので、渡された値と呼ばれないことを検証してよい（規則 3）。成功・失敗・処理中は、戻り値の Promise の resolve / reject / 解決しない Promise で作る。`vi.mock` でモジュールを差し替えない。
- **ルーター:** `Link` や `useRouter` を使うコンポーネントは、`tests/support/render-with-router.tsx` の `renderWithRouter` で描画する（`await renderWithRouter(<X />)`）。使わないものは `@testing-library/react` の `render` で描画する。
- **要素の探し方:** role と accessible name で探す（`screen.getByRole('link', { name: '場所を追加' })`）。クラス名・DOM の入れ子・`data-*` 属性に依存しない。
- **操作:** `userEvent.setup()` を描画の前に呼び、返った `user` で操作する（`await user.click(...)`）。
- **AAA:** 表示のテストは描画を Act にする。操作のテストは、前段の入力を Arrange に置き、検証したい結果を起こす最後の 1 操作を Act にする。
- **置き場所:** `src/routes/places/-components/place-form.tsx` のテストは `tests/routes/places/-components/place-form.test.tsx`。

## 判断に迷ったとき

テストを書くか、どう書くかに迷ったら、次の4つで比べる。このうちリファクタリング耐性は妥協しない。

- **退行に対する保護:** バグが入ったときに落ちるか。重要で複雑なロジックを通るテストほど高い。
- **リファクタリングへの耐性:** 振る舞いを変えない変更で落ちないか。
- **迅速なフィードバック:** 速く実行できるか。
- **保守のしやすさ:** 読みやすく、準備が短いか。
