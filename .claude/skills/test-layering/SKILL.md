# テストのレイヤーの割り当て

テストの種類に優劣は無い。種類ごとに、検出できる不具合が違う。本スキルの目的は、不具合の種類ごとに、それを検出できる最も速いレイヤーを1つ割り当て、同じ不具合を複数のレイヤーで重ねて検証しないことである。

## 適用範囲

- 決めるのは、どの種類の不具合をどのレイヤーで検出するかだけである。各レイヤーの書き方は、割り当て表の「書き方」列のスキルに従う。
- 割り当て表は本スキルだけに置く。他のスキルは本スキルを参照し、表を書き写さない。
- 探索的テストの実施方法（誰が・いつ行うか）は扱わない。
- 新しく書くテストに適用する。既存のテストの見直しは、依頼の範囲に含まれるときだけ行う。

## 割り当て表

| 不具合の種類 | 検出するレイヤー | 書き方 |
|---|---|---|
| 値の取り違え・種類の網羅漏れ・チームのルール違反 | 型・lint | `code-design` |
| 計算・変換の誤り（境界値を含む） | 単体テスト | `unit-test-plan` |
| 1つの画面の中の表示・操作の誤り（渡したデータの見え方、操作に対する表示とコールバックの呼ばれ方） | 単体テスト | `unit-test-plan` の「画面の単体テスト」 |
| 状態遷移の組み合わせの誤り・ドメインの不変条件の違反 | PBT | `unit-test-plan` |
| DB・永続化・サービス間のインタフェースの誤り | E2E（integration テストを導入するまで。#48） | `e2e-test-plan` |
| 画面をまたぐ結合・実ブラウザ・実行環境の差による誤り | E2E | `e2e-test-plan` |
| 仕様の漏れ・想定外のユースケース | 探索的テスト | 扱わない（#46） |

- 速いレイヤーは型・lint・単体テスト・PBT、遅いレイヤーは E2E である。
- 画面の不具合のうち、1つの画面の中の表示・操作の誤りは単体テスト、画面が実バックエンドのデータで開けるか・画面の遷移・ログインは E2E が受け持つ。
- 計算・変換の誤りでも、入力の範囲が広ければ PBT で検証する。入力の選び方は `unit-test-plan` 規則8に従う。

## 設計の手順

実装計画のテスト方針を書く前、またはテストを書き始める前に通す。

1. **起こりうる不具合を書き出す。** 要件と設計から、この変更で入りうる不具合を挙げ、割り当て表の種類に分ける。
2. **型・lint で書けなくできるものを先に除く。** 値の取り違え・種類の網羅漏れ・チームのルール違反は、テストを書く前に `code-design`（規則4・5・11）に従って、型・lint で書けなくする。書けなくした不具合（書いた時点で型エラー・lint エラーになるもの）には、テストを書かない。
3. **残りを、検出できる最も速いレイヤーに1つずつ割り当てる。** 割り当て表に従う（規則1）。
4. **割り当てたレイヤーのスキルで、テストの対象とケースを決める。**

完了条件: 書き出した不具合の全てに、書けなくする設計か、検出するレイヤーが1つずつ割り当たっている。

## 規則

### 1. 不具合を、検出できる最も速いレイヤーに割り当てる

**症状:** 計算の境界値を E2E で確かめている。同じ不具合を、単体テストと E2E の両方で検証している。「E2E のほうが本番に近いから確実」のように、テストの種類を優劣で選んでいる。

**直し方:** 割り当て表で、その不具合の種類を検出できるレイヤーを選ぶ。複数のレイヤーで検出できるなら、最も速いものを1つ選ぶ。遅いレイヤーには、速いレイヤーでは検出できない種類だけを置く。

**なぜ:** 速いレイヤーほど、落ちたときに原因の箇所が狭く、変更のたびに実行できる。速いレイヤーで検出できる不具合を遅いレイヤーに置くと、フィードバックが遅れ、落ちたときの切り分けも難しくなる。

### 2. 速いテストは変更のたびに全部実行し、遅いテストは結合と実環境の確認に絞る

**症状:** 変更した箇所に関係しそうなテストだけを選んで実行している。E2E が、速いテストで検出できる不具合まで受け持ち、数が増えている。

**直し方:**

- 型・lint・単体テスト・PBT は、コードを変更するたびに全部実行する。このリポジトリでは `pnpm check`（lint・format・型チェック・単体テスト）である。
- E2E（`pnpm test:e2e`）に置くのは、結合と実環境の確認だけにする。何を残すかは `e2e-test-plan` 規則1に従う。

**なぜ:** 速いテストの結果は、AI が次の変更を決めるためのフィードバックになる。毎回全部を実行すれば、変更が離れた場所を壊したことにもすぐに気づける。

### 3. 不具合を直したら、再発を防ぐ場所を決める

探索的テストで見つけたものに限らず、全ての不具合の修正に適用する。

**症状:** 不具合を直したあと、その1件だけを再現するテストを E2E に足して終えている。テストも型も足さずに終えている。

**直し方:**

1. その不具合が、なぜ書けてしまったかを考える。
2. 型・lint で書けなくできるなら、そうする（`code-design` 規則11）。
3. 書けなくできなければ、同じ種類の不具合をまとめて検出できる、最も速いレイヤーにテストを足す（規則1）。

**なぜ:** 1件を再現するだけのテストは、同じ種類の不具合が別の箇所に入っても検出しない。書けなくすれば、同じ種類の不具合がどこにも入らなくなる。

### 4. 人が型の定義と性質だけを見れば信頼できるテストにする

AI がテストを書くときの目標である。人がどうレビューするかは、本スキルでは定めない。

**症状:** 人が1件ずつ読まないと信頼できないテストになっている。手で選んだ入力が並ぶだけで、選ばれていない入力が正しいかは分からない。不正値のケースが、値を受け取る全ての関数のテストに重複している。テストが、実装を壊したときに本当に落ちるかを確かめていない。

**直し方:** 次の形にする。各項目の書き方は、参照先のスキルに従う。

- ドメインの制約を持つ値は、プリミティブ型ではなく brand 型で受け取り、不正値・境界値はパース関数のテストで1回だけ確かめる（`code-design` 規則4、`unit-test-plan` 手順3）。
- 状態と種類は判別可能な union で表し、分岐の網羅は lint に任せる（`code-design` 規則5）。
- 取りうる値が有限の型だけでできた関数は入力を全て列挙し、範囲の広い型は PBT で性質を検証する（`unit-test-plan` 規則8）。
- 書いた単体テストは、実装をわざと壊して落ちることを確かめる（`unit-test-plan` 手順5）。書いた E2E の assert は、対応する不具合を入れて、速いテストで検出できないことを確かめる（`e2e-test-plan` 手順5）。

**なぜ:** AI が書くテストの量は、人が1件ずつ読める量を超える。この形にすれば、テストを信頼する根拠が、型の定義と、テストが確かめる性質（PBT の性質を表す1文、全列挙の表）に集まる。人が確かめるのは、それらが仕様として正しいかだけになる。
