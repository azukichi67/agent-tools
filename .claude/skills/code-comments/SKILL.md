# 情報の置き場所の書き分け

## 4つの置き場所

情報が正しい場所に無いと、読み手はそれを見つけられないか、見つけても実態とずれた古い記述を信じてしまう。書く前に、その情報がどこに属するかを決める。

| 置き場所 | 答える問い | 中身 |
|---|---|---|
| コード | How | 処理をどう組み立てて実現しているか |
| テストコード | What | 正しい振る舞いとは何か |
| コミットログ・PR | Why | 変更がなぜ必要になったか |
| コードコメント | Why not | ほかの書き方をなぜ選ばなかったか |

コードコメントの役目は、意図して書かなかった処理や選ばなかった方法を伝えることにある。実際に行っている処理はコード自身が示しているので、コメントでも同じことを説明すると、2か所を揃えて保守し続けることになる。

出典: t_wada 氏の投稿（2017年9月5日、https://x.com/t_wada ）

## コメントの前に試すこと

コードを書き換えても、コメントは自動では追従しない。そのため、コメントは時間とともに実装と食い違っていく。コードの形で伝えられる情報は、コメントに頼らずコードで伝える。次を順に試す。

1. 名前を付け直して、説明そのものを不要にする（`code-naming`）
2. 一連の処理を関数に切り出し、その関数名に意図を語らせる
3. 計算の途中結果を、意味が分かる名前の変数に入れる
4. 生の数値や文字列を、名前付きの定数にする

これらを試しても伝えきれない情報だけを、コメントとして残す。

## コードコメントに書くこと（Why not）

対象は、コードを読むだけでは分からず、しかもその箇所を変更する人が知らないと誤った変更をしてしまう情報に限る。

- **意図的に省いた処理。** 抜けているように見えるが、わざと入れていない処理。
- **不自然に見える書き方の事情。** 外部 API の仕様による制約、既知のバグを避けるための回り道、性能を優先した妥協など。
- **検討して退けた別案と、その理由。** 同じ改善案を思いついた人が、検討をもう一度やり直さずに済む。
- **制約の根拠。** 公式ドキュメントの URL、Issue 番号、計測した結果。前提がまだ有効かを後から確かめられる。

例:

```ts
// キー入力のたびに検索 API を呼ばないのは、1 文字ずつリクエストが飛ぶと
// レート制限（毎秒 5 回）に掛かるため（https://example.com/docs/rate-limits ）。
const SEARCH_DEBOUNCE_MS = 300;
```

```ts
// `new Date(dueDateText)` で読まないのは、`YYYY-MM-DD` だけの文字列が UTC の 0 時として
// 解釈され、日本時間では前日になるため（ECMAScript 仕様の Date Time String Format）。
const dueDate = parseLocalDate(dueDateText);
```

## コードコメントに書かないこと

| 書かないもの | 書かない理由 |
|---|---|
| コードを言葉で言い直しただけの説明 | コードを直したときに説明だけが取り残され、食い違う |
| 変更の履歴・書いた日付・書いた人 | バージョン管理にすでに記録されている |
| コメントアウトして残したコード | 削除する。必要になればバージョン管理から取り出せる |
| 引数の名前を並べただけの決まり文句の説明 | 何も伝えないうえ、コメントを読み飛ばす癖を読み手に付ける |
| 期限も担当者も決まっていない「あとで直す」 | Issue に起こす。コードの中に置くと誰も手を付けない |

## テストコード（What）

テストは、その機能の仕様書として読まれる。**テストの名前だけを上から順に読めば、機能の振る舞いが把握できる**ようにする。

- 名前には、前提となる状態、行う操作、期待する結果の3つを含める。
- 1つのテストが確かめる結果は、ひと言で説明できる量にとどめる。
- 実現方法の詳細をテスト本体に詰め込まない。準備の手順が長いときは補助関数に移し、本体には確かめたい内容だけが見える状態にする。
- 期待値の根拠が読み手に分からないときに限り、コメントで補う。

```ts
it('在庫が 0 の商品をカートに入れようとすると、カートの中身は変わらない', () => { /* … */ });
test('有効期限を過ぎたクーポンは、合計金額から差し引かれない', () => { /* … */ });
```

## コミットログ・PR（Why）

**変更の中身は差分を見れば分かる。変更した理由は、差分のどこにも書かれていない。**

- コミットの表題には、その変更が何をするものかを1行で書く。
- 本文には、変更が必要になった事情と、それで解消する問題を書く。
- 設計の選択をしたときは、採った案、退けた案、そう決めた理由を書く。
- 判断の前提になった Issue・ドキュメント・計測結果を示す。

## 実装計画にある判断理由の移し先

実装計画や設計文書は、実装が終わると手入れされずに古びるか、不要になって消される。**そこにだけ書かれた理由は、やがて誰にも読めなくなる。**

実装計画に判断の理由があれば、移し先を決める。

| 理由の種類 | 移し先 |
|---|---|
| その行やブロックを変更する人が知っておかないと誤る | コードコメント |
| 変更全体を通した背景で、特定の行には結び付かない | コミットログ・PR 本文 |

どちらにも当たらない理由は、実装が済んだ時点で役目を終えているので移さない。

## 書き終えたら確かめること

- [ ] コードを日本語に置き換えただけのコメントが無い
- [ ] 名前の付け直しや関数の切り出しで不要にできるコメントが無い
- [ ] 意図的に省いた処理や退けた別案が、コメントに書かれている
- [ ] 制約や妥協の理由に、根拠（URL・Issue 番号・計測結果）が添えてある
- [ ] コメントアウトしたコードが残っていない
- [ ] 変更履歴や書いた人をコメントに書いていない
- [ ] テストの名前を並べて読むと、仕様が分かる
- [ ] コミットログ・PR 本文に変更の理由が書かれていて、差分の言い換えで終わっていない
- [ ] 実装計画の中にしか無い判断理由が残っていない
