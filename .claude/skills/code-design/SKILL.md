# コードの設計

設計の目的は、仕様変更のときに直す場所を1か所にすることである。関連するデータとロジックが散らばっていると、変更のたびに全ての箇所を探すことになり、1か所でも直し忘れればバグになる。

## 適用範囲

- 命名は `code-naming`、コメントは `code-comments` に従う。本スキルは扱わない。
- 新しく書くコードに適用する。既存コードの設計変更は、依頼の範囲に含まれるときだけ行う。範囲外の構造変更は、変更差分を膨らませてレビューを困難にする。
- 本スキルの「クラス」は、TypeScript ではクラスに限らない。型と、その型を扱う関数を集めたモジュールでもよい。要は、あるデータとそれを操作するロジックの置き場所が1か所に決まっていること。
- 各規則の「適用しない場合」に当てはまるときは、規則より読みやすさを優先する。規則は目的を果たす手段であり、目的に反するなら使わない。

## 設計の手順

実装計画を書く前、またはコードを書き始める前に通す。

1. **関心事を1文にする。** その型・モジュールが何の目的のために存在するかを書く。「商品」のような存在ではなく、「予約する商品」「発送する商品」のような目的で書く。1文に収まらなければ、関心事が複数混ざっている。
2. **データとロジックの置き場所を1つ決める。** 手順1の関心事に関わるデータと、そのデータを使う計算・判定・変換を同じ場所に置く（規則1）。
3. **不変条件を書き出し、生成時に守る。** 「金額は0以上」「開始日は終了日より前」のように、そのデータが常に満たすべき条件を列挙し、生成時に検査する（規則2）。
4. **誤りを書けなくできないか検討する。** テストで検出する前に、値の取り違えは専用の型（規則4）で、種類の網羅漏れは判別可能な union と lint（規則5）で、型で表せないチームのルールは lint ルール（規則11）で、書いた時点でエラーになるようにする。
5. **分岐と依存を確認する。** 同じ種類の条件分岐が複数の場所に現れないか（規則5）、関心事の異なるモジュールに依存していないか（規則7）を確認する。

## 規則

### 1. データとロジックを同じ場所に置く

**症状:** データだけを持つ型と、そのデータを外から読んで計算する関数が別々の場所にある。同じ計算があちこちで重複する。

**直し方:** データを使う計算・判定を、データを持つ側に置く。呼び出し側はデータを取り出して判断せず、処理を命じるだけにする（尋ねるな、命じろ）。

**なぜ:** ロジックが散らばると（低凝集）、仕様変更のたびに全ての箇所を探して直すことになる。

**適用しない場合:** 画面表示やシリアライズのように、データを外へ渡すだけの境界では、データだけの型でよい。

### 2. 生焼けオブジェクトを作らない

**症状:** 生成したあとに初期化関数を呼ぶ、またはプロパティを後から埋めないと使えない。不正な値のまま生成できる。

**直し方:** 生成時に全ての値を受け取り、不変条件を満たさない値では生成できないようにする（完全コンストラクタ）。不変条件を満たさない値を渡されたら、その場で失敗にする（失敗を表す戻り値、または例外。規則8）。TypeScript では、zod の `.brand()` による brand 型と、そのスキーマで検査するパース関数で書く（規則4）。クラスの private コンストラクタと static の生成メソッドで書く方法もあるが、このリポジトリの標準ではない（`references/examples.md` に参考として載せる）。

**なぜ:** 不正な状態で存在できるなら、使う側の全ての箇所で検査が必要になり、1か所でも漏れればバグになる。

### 3. 不変を基本にする

**症状:** 1つの変数に意味の違う値を順に再代入する。引数や共有されたオブジェクトを書き換える。

**直し方:** 変数・プロパティは `const` / `readonly` にする。値を変えるときは、新しい値を作って返す。意味の違う値にはそれぞれ別の変数を用意する。

配列とオブジェクトの操作は、次のように書き分ける。

- **ネイティブで書く:** 元の配列を書き換えないメソッド（`map` / `filter` / `find` / `some` / `every` / `join` など）。
- **remeda で書く:** 元の配列を書き換えるネイティブのメソッドの代わり（`sort` / `reverse` / `splice` → `R.sort` / `R.sortBy` / `R.reverse` など）と、ネイティブに無い関数（`groupBy` / `pick` / `omit` / `partition` / `indexBy` など）。`toSorted` などのネイティブの不変メソッドは使わない（tsconfig の `lib` が `ES2022` で型定義が無い。並べ替えは remeda に揃える）。
- import は `import * as R from 'remeda'` にし、名前付き import にしない。`R.` で remeda の関数だと分かり、ネイティブのメソッドやローカル変数と名前がぶつからない。
- 1回の操作は data-first で書く（`R.sort(sources, compareByName)`）。remeda の関数を2つ以上つなぐときだけ `R.pipe` を使う（`R.pipe(fooById, R.omit(['draft']), R.mapValues(toBar))`）。
- `R.sortBy` は `>` / `<` で比べるだけで、`localeCompare` を使わない。`'ja'` ロケールの読み順で並べるなら、`R.sort(data, 比較関数)` で書く。

**なぜ:** 値がどこで書き換わるかを追えなくなり、ある時点の値を読み違える。共有されたオブジェクトの書き換えは、離れた場所で予期しない不具合を起こす。

**適用しない場合:** 関数の中に閉じたループの集計変数は、再代入してよい。外から見えない再代入は追跡の負担が小さく、変数を増やすほうが読みにくくなる。

### 4. ドメインの制約を持つ値は専用の型にする

**症状:** 金額・数量・日付範囲のような制約を持つ値を `number` や `string` のまま扱い、制約の検査があちこちで重複する。別の意味の値を取り違えて渡しても型検査を通る。

**直し方:** 値と、その値の制約を1つの型にまとめる（値オブジェクト）。TypeScript での標準の書き方は、zod の `.brand()` による brand 型と、そのスキーマで検査するパース関数である。

```ts
import * as z from 'zod'

const moneySchema = z.int().nonnegative().brand<'Money'>()

export type Money = z.infer<typeof moneySchema>

export const parseMoney = (amount: number): Money | null => {
  const parsedMoney = moneySchema.safeParse(amount)
  return parsedMoney.success ? parsedMoney.data : null
}
```

- brand 型の値を作る手段は、パース関数だけにする。`as` で brand 型に変換しない。テストコードでも、パース関数を通して作る。
- その値に固有の計算は、同じモジュールに関数として置く。結果もパース関数を通して brand 型にし、通らなければ規則11の形のメッセージで例外を投げる。スキーマの `.parse()` で brand 型にしない（zod 既定のメッセージの例外になる）。
- 不変にする（規則3）。オブジェクトと配列のスキーマには `.readonly()` を付ける。

**なぜ:** 制約の検査がパース関数の1か所に集まり、不正な値が存在できなくなる。別の意味の値を取り違えたときに型エラーになる。brand 型の値はパース関数を通さないと作れないので、不正値・境界値のテストはパース関数のテストで1回だけ書けばよく、brand 型を受け取る関数のテストには不正値のケースを書かない。

**適用しない場合:** 制約も固有の計算も無い値。ラップすると演算子で計算を書けなくなり、式がかえって読みにくくなるもの。ラップするかは、守りたい制約があるかで決める。

### 5. 条件分岐を1か所に集める

**症状:** if 文が深く入れ子になる。同じ種類による switch / if が、複数の関数に散らばっている。

**直し方:**

- 入れ子は、条件を満たさない場合に先に return して浅くする（早期 return）。
- 同じ種類による分岐が複数の場所に現れたら、種類ごとの振る舞いを interface の実装か判別可能な union にまとめ、分岐を1か所に集める（ストラテジパターン）。
- 「全て満たせば可」のような複数ルールの判定は、ルールを1つずつ型にして、まとめて評価する型を用意する（ポリシーパターン）。
- 判別可能な union の種類による分岐は、switch で書く（if の連鎖は lint が網羅を検査しない）。case の網羅は lint に任せる。このリポジトリでは `biome.json` で Biome の `useExhaustiveSwitchCases` を `requireExplicitCase: true` で有効にしており、`default` 節がある switch でも欠けた case を error にする。`never` への代入による網羅の検査（`const unreachable: never = value`）は書かない。

**なぜ:** 種類を追加したときに、散らばった分岐の全てを探して直すことになる。1か所でも漏れればバグになる。`never` への代入は、書き忘れた switch では何も検出せず、書き忘れたこと自体も静的に検出できない。また tsc は、戻り値の型が `undefined` を含む関数（React コンポーネントなど）の switch では、網羅漏れを検出しない。lint は全ての switch を検査する。

**適用しない場合:** 分岐が1か所にしか現れないなら、switch のままでよい。switch を Map（オブジェクト）に置き換えても分岐の数は減らない。見た目が変わるだけなので、それだけを目的に置き換えない。

### 6. コレクションを包む

**症状:** 配列をそのまま外に渡し、要素の追加・削除や制約の検査を呼び出し側のあちこちで書いている。

**直し方:** 配列と、その配列に対する操作・制約を1つの型にまとめる（ファーストクラスコレクション）。外に渡すときは `readonly` の配列として渡す。

**なぜ:** 規則1と同じく、配列に対するロジックが散らばると、上限などの制約の検査が漏れる。

### 7. 結合を弱くする

**症状:** 継承した親クラスを変えると子クラスが壊れる。1つの型に関心事の違うロジックが集まり、何にでも使われる（神クラス）。

**直し方:**

- 振る舞いの再利用は継承ではなく、部品を持たせる形で行う（コンポジション）。
- 1つの型・モジュールが担う目的は1つにする（単一責任）。関心事が違うなら、同じデータに見えても型を分ける。
- 外に公開するのは、外から使うものだけにする。

**なぜ:** 依存が多いほど、1か所の変更が他の箇所を壊す。

**適用しない場合:** 分けすぎると、1つの処理を読むために参照する定義が増える。分割の単位は、ドメインで実際に使われている言葉の区切りに合わせる。統合したほうが扱いやすいなら、統合も良い設計である。

### 8. 関数の引数と戻り値を絞る

- 状態を変える関数（コマンド）と、値を返す関数（クエリ）を分ける。
- 真偽値のフラグ引数で処理を切り替えず、関数を分ける。
- 引数を書き換えて結果を返さない（出力引数）。結果は戻り値で返す。
- null / undefined を引数に渡す設計にしない。無いことに意味があるなら、それを表す型を用意する。
- 引数が多くなったら、関連する引数を1つの型にまとめられないかを検討する。
- 失敗は握りつぶさず、呼び出し側に伝わる形で返す（例外、または失敗を表す戻り値の型）。

**なぜ:** 呼び出し側が関数の中身を読まずに、何が起きるかを判断できるようにするため。

### 9. 設計を壊すものを入れない

- **デッドコード:** 到達しないコードは消す。読み手に意味を探させる。
- **YAGNI:** 今の要件に無い機能・拡張点を先回りして作らない。
- **マジックナンバー:** 意味のある数値・文字列には名前を付けた定数を使う。
- **文字列型への執着:** 区切り文字で複数の値を1つの文字列に詰めない。種類は文字列ではなく union 型にする。
- **グローバルな可変状態:** 状態は、使う範囲を最小にして持つ。
- **例外の握りつぶし:** catch したら、処理するか、上位に伝えるかのどちらかにする。
- **コピペ:** 同じロジックを複製しない。ただし、見た目が同じでも関心事が違うなら、まとめずに別々にしておく。

### 10. リファクタリングは機能追加と分ける

- 機能追加とリファクタリングを同じ変更に混ぜない。振る舞いが変わった原因を切り分けられなくなる。
- 先にテストで今の振る舞いを固定してから、構造を変える。
- 1回の変更を小さくし、変更のたびにテストを通す。

### 11. テストより先に、誤りを書けなくする

**症状:** 値の取り違え・種類の網羅漏れ・チームのルール違反を、テストやレビューで見つけようとしている。開発者向けのエラーメッセージが「不正な値」のように、何がどう悪いのかを伝えない。

**直し方:**

- 値の取り違えは専用の型（規則4）で、種類の網羅漏れは判別可能な union と lint（規則5）で、書いた時点で型エラー・lint エラーになるようにする。
- 型で表せないチームのルールは、lint ルールの追加を提案する。追加するかはユーザーに確認する。
- 開発者向けのエラー（不変条件違反の例外など）のメッセージには、どのルールに、どの値が、どう違反したか、どう直すかを書く。

```ts
throw new Error(
  `取り消せるのは status が "pending" の注文だけだが、status が "${status}" の注文が渡された。"pending" の注文だけを渡す`,
)
```

- 利用者向けの検証メッセージ（zod の `error` で画面に出す文言）は、前項の対象外とする。値やルール名を画面に出すと使い勝手を損ない、入力値をそのまま画面に表示する経路も増えるため。

**なぜ:** テストは、書いたケースの誤りしか検出しない。型と lint は、全ての箇所を書いた時点で検査し、変更のたびに速く結果を返す。エラーメッセージに違反の内容と直し方まであれば、AI はメッセージだけで次の修正を決められる。

## 書き上げたあとのチェック

- [ ] 1. データを外から取り出して計算・判定しているロジックが、データを持つ側に置かれているか
- [ ] 2. 生成直後から全ての値が揃い、不変条件を満たさない値では生成できないか
- [ ] 3. 意味の違う値の再代入や、引数・共有オブジェクトの書き換えが無いか
- [ ] 4. 制約を持つ値が brand 型になり、その検査がパース関数に集まり、`as` やスキーマの `.parse()` で brand 型を作っていないか
- [ ] 5. 同じ種類による分岐が散らばっていないか。union の分岐が switch で書かれ、`never` による網羅の検査を書いていないか
- [ ] 6. 配列に対する操作・制約が、呼び出し側に散らばっていないか
- [ ] 7. 1つの型・モジュールが、複数の関心事を担っていないか
- [ ] 8. フラグ引数・出力引数・null を渡す設計・握りつぶされた失敗が無いか
- [ ] 9. デッドコード・先回りの実装・マジックナンバー・ロジックの複製が無いか
- [ ] 10. リファクタリングと機能追加が、同じ変更に混ざっていないか
- [ ] 11. 型・lint で書けなくできる誤りを、テストに任せていないか。開発者向けのエラーメッセージに、ルール・値・違反の内容・直し方が書かれているか
