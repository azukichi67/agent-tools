# Issueの実装計画を作る

## 手順

1. $ARGUMENTS からIssue番号とスコープを取得する。Issue番号が無ければユーザーに確認する。スコープが無ければ「Issue 全体」とする。
2. 下の「依頼文」の `<番号>` と `<スコープ>` を埋め、`docs/design-for-ai/issue<番号>-<内容の英語要約>-request.md`（スコープがPR単位の場合は `issue<番号>-pr<番号>-<内容の英語要約>-request.md`）に保存する。このファイルは計画レビュー（`/plan-review-loop`）の要件ファイルとして使う。
3. 依頼文に従って実装計画を作成する。
4. 作成した実装計画について、自分でレビューと改善を3回繰り返す。
5. Skill tool で `explain-visually` を呼び出し、args に実装計画のパスを渡して、人間が読むための解説HTMLを生成する。
6. 実装計画・依頼文・解説HTMLのパスを報告し、次の工程を案内する。
   - 解説HTMLをホストのブラウザで読み、不明点はこのセッションで質問する（「D-03を詳しく」のように識別子で深掘りできる）。計画の中身を自分の言葉で説明できるまで潰す。計画の修正が必要なら、このセッションで指示する
   - 理解とレビューが終わったら、新しいセッションで `/plan-review-loop <実装計画> <依頼文>` を実行する

## 依頼文

```markdown
# 依頼内容

以下の GitHub Issue に対する実装計画を作成してください。

- 対象 Issue: #<番号>
- 今回のスコープ: <スコープ>

Issue には要件が言語化済みで、解決に必要な情報は Issue 内に揃っています。本文とコメントを `gh` コマンドで全て取得して読んでください。

# 成果物

- 配置先: `docs/design-for-ai/` 配下のマークダウンファイル 1 つ
- ファイル名: `issue<番号>-<内容の英語要約>-implementation-plan.md`（スコープが PR 単位の場合は `issue<番号>-pr<番号>-<内容の英語要約>-implementation-plan.md`）

この実装計画は、本セッションの文脈を持たない別の AI コーディングエージェントがそのまま実装に使います。人間が読むことは想定していません。追加の調査や質問なしで実装に着手できる、それ単体で完結した内容にしてください。

構成・フォーマットは指定しません。課題ごとに最適な書き方は異なるため、この課題に最適だと考える形で書いてください。

実装計画内にコードブロック（実装例・変更後のコード等）を書く場合は、先に以下の Skill を読み込み、その内容に従って命名とコメントを書いてください。

- `code-naming`: 変数・関数・メソッド・クラス・型・ファイルの命名規則
- `code-comments`: コード・テストコード・コミットログ・コードコメントの書き分け

Skill の実体はどちらも `.claude/skills/<skill名>/SKILL.md` にあります。Skill を自動発見できない環境の場合は、このパスのファイルを直接読んでください。

設計（責務の分割、データの持ち方、条件分岐、依存関係）を決める際は、先に `code-design` Skill を読み込み、その内容に従ってください。実体は `.claude/skills/code-design/SKILL.md` にあります。

テスト方針を決める前に、`test-layering` Skill を読み込み、その内容に従って不具合の種類ごとに検出するレイヤーを割り当ててください。実体は `.claude/skills/test-layering/SKILL.md` にあります。

テスト方針を決める際は、先に `unit-test-plan` Skill を読み込み、その内容に従ってください。実体は `.claude/skills/unit-test-plan/SKILL.md` にあります。

E2E テストの方針を決める際は、`e2e-test-plan` Skill も読み込み、その内容に従ってください。実体は `.claude/skills/e2e-test-plan/SKILL.md` にあります。

実装計画に必ず含めるもの:

- 変更対象ファイルの一覧と、それぞれの変更内容
- 利用するライブラリ API の、現在インストールされているバージョンでの正しい書き方（根拠として参照した一次情報の URL を併記する）
- テスト方針（不具合の種類ごとの検出レイヤーの割り当て、テスト対象・配置場所・観点）
- 品質管理の手順（package.json の scripts と CLAUDE.md から、この変更で実行すべきテスト・lint・型チェックを特定して書く）
- ブラウザでの動作確認手順（操作手順と期待する結果まで書く）

`docs/design-for-ai/` に過去の実装計画が残っている場合がありますが、古い前提を含んでいる可能性があるため参照しないでください。事実確認は現行のコードと一次情報で行ってください。

# 進め方の境界

- コードの読解・`gh` での Issue 取得・ドキュメント調査は、確認なしで進めてください
- Issue の記述と実際のコードが矛盾している場合や、要件の解釈次第で設計が大きく変わる場合は、推測で確定せず私に確認してください

# 環境情報

- 開発サーバーは起動済みとは限りません。動作確認が必要なら自分で起動してください
- ドキュメント調査の手段は指定しません。このセッションで利用可能なツール（MCP・Skill・Web 検索等）から最適なものを選んでください

# 提出前のセルフチェック

書き終えたら、実装を担当する AI コーディングエージェントの視点で通読し、以下を満たしていることを確認してから提出してください。

- 実装計画に登場するファイルパス・関数名・DB カラム名が全て実在する（新規作成するものはその旨が明記されている）
- 実装計画単体で実装に着手できる（本セッションでしか分からない前提が残っていない）
```
