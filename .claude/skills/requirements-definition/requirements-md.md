# requirements.md の章立てと書き方

`requirements.html` で決まったことを固定する文書。ユーザーが最終チェックとして通読する。

## 章立て

```
# <Issue のタイトル>

Issue: #<番号> / 画面イメージ: requirements.html

## 機能
## 今回つくらないもの
## 画面
## 例外ケース
## 非機能要件（Issue が関わるときだけ）
## 確認事項（未決があるときだけ）
```

## 機能

「〜できる」の箇条書きで書く。実装方法は書かない。

- 名前を入力して項目を登録できる（名前以外は任意）

### 優先度は MoSCoW で決める

1つの Issue で複数の機能に優先度をつけるときに使う。

| 分類 | 意味 | 割合の目安 |
|---|---|---|
| Must | なければ成り立たない | 〜60% |
| Should | ないと困るが、なくても最低限は動く | 〜20% |
| Could | あれば嬉しいが、なくても許容範囲 | 〜20% |
| Won't | 今回はやらない | - |

**Must が6割を超えたら、優先順位がついていないと考える。** 「全部必須」は「優先順位なし」と同じ。

ユーザーが全部 Must にしようとしたら、トレードオフを数字で見せて判断を促す。

- 「この機能を足すと、動くものが見えるまで◯日遅れます。それでもいいですか？」
- 「Must を3つに絞るとしたら、どれを残しますか？」

Won't にした機能は「今回つくらないもの」に書く。

### ユースケース

複雑な機能だけ詳細化する。単純な CRUD には書かない。

| 項目 | 内容 |
|---|---|
| アクター | 誰が使うか |
| 事前条件 | この機能を使う前の状態 |
| 基本フロー | 正常な流れ |
| 代替フロー | 分岐する場合の流れ |
| 例外フロー | エラーの場合の流れ |
| 事後条件 | この機能を使った後の状態 |

**例外フローが埋まらない機能は、要件が固まっていない。** SKILL.md の「例外を引き出す」を先にやる。

## 今回つくらないもの

必ず置く。スコープ外を明記しないと、読み手（実装者と Claude）が勝手に補完する。理由も1行添える。

## 画面

画面ごとに、表示する内容と、できる操作を書く。

同じ言葉が別物を指すため、次のような語は必ず具体化する。

| 文章での定義 | 解釈A | 解釈B |
|---|---|---|
| 一覧表示 | 10件ずつページング | 全件を無限スクロール |
| 検索機能 | テキストボックス1つ | 日付・ステータス等の複合検索 |
| 編集可能 | 別画面で編集 | 一覧上で直接編集（インライン） |
| ステータス表示 | テキストで「承認済」 | 色付きバッジでアイコン表示 |

文章で書けば「一覧表示」の5文字で済むが、実装するには決めることが100個ある。決まっていない項目は Claude が実装時に勝手に決めることになる。

## 例外ケース

例外ケースごとに、決めた挙動と理由を書く。

## 非機能要件

機能要件が「何をするか」なら、非機能要件は「どのくらいのレベルで」。Issue が非機能要件に関わるときは、6カテゴリすべてに言及する。検討した結果「不要」なら、不要と書く。

| カテゴリ | 内容 |
|---|---|
| 可用性 | どのくらい止まらないか |
| 性能 | どのくらい早いか |
| 拡張性 | 将来の拡張に対応できるか |
| 運用保守 | 運用しやすいか |
| 移行性 | データ移行できるか |
| セキュリティ | 安全か |

### 「普通でいい」で済ませない

『普通』の定義は人によって違う。数値か、検証可能な条件で書く。

### 「当たり前」こそ明文化する

書いていないものは、実装時に「やらなくていい」と解釈される。

- 日本語で表示される
- ブラウザの戻るボタンが使える
- スマートフォンの画面幅で横スクロールが出ない
- タイムアウトしたら再ログインが必要

### 全部を最高レベルにしない

システムの特性に合わせてメリハリをつける。利用者数・データ量・止まったときの影響から水準を決める。**高い水準を置かないと決めたことも、決定として書く。**

## 確認事項

書き方は SKILL.md の「未決事項は確認事項に書く」に従う。
