# 要件定義

要件定義は常に Issue 単位で行う。全体の要件定義も、そのための Issue を切って行う。

生成するファイルは次の2つだけ。

| ファイル | 役割 |
|---|---|
| `docs/requirements/issue<番号>-<英語 kebab-case 要約>/requirements.html` | 画面を見ながら決めるための画面イメージ。合意後は更新しない |
| `docs/requirements/issue<番号>-<英語 kebab-case 要約>/requirements.md` | 決まったことを固定する文書。最終チェックに使う。**正はこちら** |

## 手順

### 1. Issue と前提を確かめる

- Issue 番号を引数から取る。無ければユーザーに確認する
- `gh issue view <番号>` で Issue を読む
- Issue に関わる既存の画面・データをコードから読む

完了条件: Issue の目的と、関わる既存の画面・データを説明できる。

### 2. 作り直しになる分岐を聞く

画面より先に決めるのは、あとから変えるとデータの持ち方が変わる分岐だけ。文言・配色・レイアウト・表示位置は画面を見ながら決めた方が速いので、ここでは聞かない。

番号付きで、yes / no で答えられる形にして1〜2個だけ聞く。

- 悪い例: 「どんな一覧にしたいですか？」（返事が遅く、曖昧な答えが返る）
- 良い例: 「1. 1つの注文に複数の配送先を持たせますか？（yes / no）」

完了条件: データの持ち方が変わる分岐が残っていない。

### 3. `requirements.html` を作る

[template.html](template.html) を複製し、[requirements-html.md](requirements-html.md) に従って埋める。文章化はまだしない。

画面の作りは `ui-design` Skill（`.claude/skills/ui-design/SKILL.md`）に従う。

完了条件: Issue で変わる画面（画面が変わらない Issue なら決定事項）がすべて1ページに並び、`{{` が残っていない。

### 4. 画面を見ながら決める

文章の合意は誤解を隠し、画面は誤解を暴く。ユーザーと画面を見ながら「この画面でこう出る」「ここを押すとこうなる」で話す。

- 指摘は同じファイルに上書きで反映する。版ごとにファイルを増やさない
- 決まったことは「決まったこと」の表へ移す
- 「例外を引き出す」の質問もこの段階でする

完了条件: ユーザーが画面への指摘を出し切った。

### 5. `requirements.md` に文書化する

章立てと書き方は [requirements-md.md](requirements-md.md) に従う。文章は「決めるための道具」ではなく「決まったことを固定する道具」として使う。まだ決まっていないことは本文に混ぜず、確認事項に置く。

完了条件: `requirements.html` と `requirements.md` が食い違っていない。

### 6. 確認事項を解消する

「決まらないとき」に従って決める。回答は本文に反映し、画面が変わる回答なら `requirements.html` も直す。

完了条件: 確認事項の節がない。

### 7. 自己レビューする

- 同じものを別の言葉で呼んでいないか（既存のコード・画面の用語と揃っているか）
- 機能間で矛盾はないか
- 抜け漏れはないか（特に例外ケース）
- 実現可能性に問題はないか
- 曖昧な表現を排除したか
- 「今回つくらないもの」に挙げた機能が混入していないか
- 優先度をつけたなら、Must が6割を超えていないか

完了条件: すべてのチェック項目を満たしている。

### 8. 最終チェックとして通読してもらう

ユーザーに `requirements.md` を時間をかけて読んでもらう。時間をかけて読むこと自体が頭を使わせる作業で、画面では流れてしまった齟齬にここで気づける。この工程は省かない。

- 指摘があれば 5 に戻る
- 合意したら、`requirements.html` を requirements-html.md の「合意したら」に従って直す。以後 `requirements.html` は更新しない

完了条件: ユーザーが `requirements.md` に合意した。

### 9. 次の段階を案内する

`/grill-issue <番号>` を案内する。

## 大原則

**要求をそのまま要件として書かない。**

| | 要求 | 要件 |
|---|---|---|
| 定義 | ユーザーの希望・願望 | システムが満たすべき条件 |
| 特徴 | 曖昧、主観的 | 具体的、検証可能 |
| 例 | 使いやすくしたい | 3クリック以内で目的の画面に到達できる |
| 例 | 早くしたい | 検索結果が2秒以内に表示される |

要求を引き出し、整理し、要件として定義する。このプロセス全体が要件定義である。

本スキルは、発注者と受注者が同一人物の開発を前提とする。そのため要求を出すのも検証するのもユーザー本人になる。**だからこそ要求と要件の境目が消えやすい。** ユーザーの発言は要求であって要件ではない、という区別を Claude 側が保つ。

## 曖昧な言葉は、後で揉める言葉

| 悪い例 | 問題点 | 良い例 |
|---|---|---|
| 使いやすくする | 基準がない | 3クリック以内で完了 |
| 早くする | 測定できない | 応答時間2秒以内 |
| たくさん保存できる | 曖昧 | 10万件まで保存可能 |
| データを管理できる | 範囲が不明 | 登録・編集・一覧表示ができる（削除はしない） |

受発注の現場なら揉める相手は顧客だが、同一人物の開発では**未来の自分と、実装するときの Claude** が相手になる。曖昧な要件は消えてなくならず、実装時に誰かが勝手に決める。

「〇〇みたいに」という表現が出たら必ず具体化する。「Excel みたいに」は一覧編集・計算・コピペ・自由なレイアウトのどれを指すか分からない。

## 例外を引き出す

要件の抜け漏れは、ほぼ例外ケースで起きる。例外は「滅多に起きない」が「起きたら致命的」。しかもユーザーにとっては当たり前すぎて、聞かれないと言わない。

Claude 側から質問して引き出す。

| 質問 | 引き出せる例外 |
|---|---|
| 同じものを二重に登録したらどうしますか？ | 重複チェックの要否 |
| 操作を間違えたら取り消せますか？ | 取消フローの要否 |
| 登録が0件のときは何を表示しますか？ | 空状態の表示 |
| 必須項目を空のまま保存しようとしたら？ | バリデーションとエラー表示 |
| 通信が切れている出先ではどうなりますか？ | オフライン時の挙動 |
| 入力された名前が長いときはどう表示しますか？ | 折り返し・省略の扱い |

## 決まらないとき

**「あとで決めましょう」を受け入れない。** 理由は以下。

- 実装開始後は、決めている余裕がない
- 他の機能との整合性が取れなくなる
- 後から決めると手戻りが発生する
- 結局決まらず、実装時に Claude が勝手に決める

### 決断を促す

ユーザーが決められないときは、決められない理由に合わせて対処する。

| 決められない理由 | 対処 |
|---|---|
| 情報が足りない | 選択肢と、それぞれの影響を整理して見せる |
| 判断材料がない | 最悪ケースと、その場合の対策を説明する |
| どちらでもよく見える | 差が出る具体的な場面を1つ挙げる |

問いかけの型。

| テクニック | やり方 |
|---|---|
| 選択肢を絞る | 「A・B・Cの3案があります。どれにしますか？」 |
| デフォルトを提示 | 「特に指定がなければAで進めますが、よいですか？」 |
| リスクを伝える | 「決まらない場合、この部分の実装が止まります」 |
| 仮決定にする | 「一旦Aで進めて、◯◯の時点で見直しましょう」 |

**仮決定には必ず見直し時点を書く。** 「いつか見直す」は見直されない。

### 未決事項は確認事項に書く

それでも決まらなければ、`requirements.md` 末尾の「確認事項」に書く。本文に空欄で残さない。空欄は「決まっていない」ことを伝えず、読み飛ばされる。

- 並び順は「決まらないと着手できない順」
- 各項目に書くこと
  - 何が決まっていないか
  - 選択肢と、それぞれのトレードオフ（1〜2行）
  - いつまでに決める必要があるか（どの作業の前か）
  - 誰が決めるか
  - 決まらなかった場合のリスク
  - 仮の前提（あれば）

回答が出たら本文に反映し、確認事項が空になったら節ごと消す。残しておくと、まだ決まっていない機能に見える。

## 実装で仕様がずれたら

実装中の判断で、仕様は少しずれる。ずれをユーザーが合意したなら、`requirements.md` を実装に合わせて直す。要件書を、実装後も機能の説明書として使い続けるため。

- 合意がない、または実装の誤りなら、直す対象はコード
- `requirements.html` は直さない。合意した時点の画面イメージとして残す

## やってはいけないこと

| アンチパターン | なぜダメか |
|---|---|
| とりあえず実装して見せる | 家を建ててから「3階建てにして」と言われるのと同じ。手戻りのコストは工程が進むほど跳ね上がる。`requirements.html` はデータを持たない見た目だけの HTML で、これには当たらない |
| 「あとで決めましょう」を受け入れる | 結局決まらず、実装時に勝手に決まる |
| 例外ケースを「起きてから考える」 | 本番で発覚したときの修正コストが跳ね上がる |
| 全機能を Must にする | 優先順位をつけていないのと同じ |
| 「やらないこと」の蒸し返しを合意なく受ける | スコープクリープ。「これくらいなら」の積み重ねで破綻する。追加したいなら、影響を示し、Issue を切り直す |
| 曖昧なまま先へ進む | 曖昧な言葉は、後で揉める言葉 |
