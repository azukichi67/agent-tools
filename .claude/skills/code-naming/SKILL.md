# 識別子の名前の付け方

コードを読む人が最初に目にする説明は名前である。名前から処理の中身が分からないと、読み手は実装を開くまで判断できず、呼び出しの重さや副作用を取り違える。

## このスキルが決める範囲

- 決めるのは**どの語を選ぶか**に限る。camelCase・snake_case・PascalCase のような書式は、言語とプロジェクトの規約に合わせる。
- プロジェクトのコーディング規約があればそれに従うが、**語の選び方についてはこのスキルを優先する**。
- ただし次の2つは、このスキルより優先する。どちらも名前を自分で選べないため。
  1. 言語の仕組みが決まった名前を求めるもの（アクセサやプロパティ、言語が定める特殊メソッド、テストフレームワークが求める名前の付け方など）
  2. 標準ライブラリ、フレームワーク、外部ライブラリが決めている名前
- **これから付ける名前が対象。** すでにある名前は、改名が依頼に含まれるときだけ変える。頼まれていない改名をまとめて行うと差分が膨らみ、レビューしにくくなる。

## 名前を決める手順

1. **処理の内容を日本語の1文で書く。** 「〜を取得する」としか書けないなら、処理の理解が足りていない。何から、どんな方法で値を得て、その結果どうなるのかまで書く。
2. **1文の中の動詞を英語の動詞にする。** 候補に迷ったら `references/verbs.md` を見る。
3. **操作の対象を名詞にする。** 広すぎる名詞になっていないかを規則3に照らす。
4. **修飾語を足すべきか考える。** 時間・状態・確からしさなどを補う語は `references/modifiers.md` にある。
5. **口に出して読んでみる。** 英語として読めない名前は、読み手にも意味が伝わらない。真偽値は `if` の条件部分に入れて読む。

## 規則

### 1. `get` を新しく使わない

「取得」という言葉は、中で何が起きるかを一切伝えない。データベースへの問い合わせか、計算か、手元の値を返すだけか、外部サービスへの通信かが分からず、呼び出す側は処理の重さと失敗する可能性を誤って見積もる。

値をどうやって得るのかを、そのまま動詞にする。

| 値の得方 | 使う動詞 |
|---|---|
| 保存してある場所から読み出す | `load` |
| ネットワークを通して取ってくる | `fetch` |
| 条件に合うものを探す | `find` / `search` |
| 一覧にまとめて返す | `list` |
| 材料を組み合わせて作る | `build` / `compose` |
| 計算で求める | `calculate` / `count` |
| いくつかの材料から1つに絞り込む | `resolve` / `determine` |
| 別の形に変えて返す | `〜From` / `〜Of` / `to〜`（向きで選ぶ。規則9） |
| 全体の一部だけを抜き出す | `extract` |
| 無ければ作ってから返す | `findOrCreate` |

`get` を使ってよいのは、適用範囲で挙げた2つの場合（言語の仕組みとしてのアクセサ、既存のライブラリが決めた名前）に限る。それ以外で `get` を付けたくなったら、手順1に戻って処理を1文で書き直す。

### 2. 名前で処理の重さを偽らない

値を返すだけに見える軽い名前の関数に、ファイルやデータベースの読み書き、ネットワーク通信、大量の繰り返しを入れない。反対に、手元の値を読むだけの処理に重そうな動詞を付けない。名前と実際の重さが合っていないと、呼び出す側が気付かずにループの中で何度も呼ぶ。

### 3. 目的を名前に入れる（目的駆動名前設計）

意味の広い名詞を使うと、関係するあらゆる関心事の処理がそこへ集まり、クラスが際限なく大きくなる。**そのクラスがどの関心事のためにあるのかを名前に含める。**

```ts
// 会員に関わる処理がすべて流れ込む広い型
class Member {}

// 関心事ごとに分けた型
class MembershipApplicant {} // 入会の申し込み
class BillingSubscriber {} // 会費の請求
class EventAttendee {} // イベントへの参加
```

名前を分けることは、そのまま責務を分けることになる。

次の語は、役割が決まらないまま何でも放り込まれる入れ物になりがちである。使う前に、何をするものなのかを別の名詞で言えないか考える。

| 避ける語 | 言い換え方 |
|---|---|
| `〜Manager` / `〜Controller`（MVC の Controller は除く） | 管理の中身を動詞にして、その単位で分ける |
| `〜Util` / `〜Helper` | 扱う型の名前を付けた専用のクラスにする |
| `〜Data` / `〜Info` / `〜Item` / `〜Type` | 取っても意味が変わらなければ取る。変わるなら、中身がまだ決まっていない |
| `data` / `result` / `temp` / `flag` | 実際に入っている値を名前にする（`isPaid` / `createdOrderId` / `sortedScores` など） |

この考え方は『良いコード／悪いコードで学ぶ設計入門』（仙塲大也）第10章による。

### 4. 真偽値は `if` の条件に置いて英文になる名前にする

判断の基準は、**`== true` を付け足さないと文として読めない名前にしない**こと。

| 形 | 例 |
|---|---|
| `is` ＋形容詞／過去分詞 | `isClosed` / `isPublished` |
| `has` ＋名詞／過去分詞 | `hasAttachments` / `hasPaid` |
| `can` ＋動詞の原形 | `canEdit` |
| `should` ＋動詞の原形 | `shouldNotify` |
| `needs` ＋名詞／動詞 | `needsReview` |
| 三人称単数の動詞（＋名詞） | `exists` / `includes` / `matchesPattern` |

使わない形は3つある。`check〜`（真のときに何が成り立つのか読めない）、`is` ＋動詞の原形（`isFinish` ではなく `isFinished`）、動詞の原形＋名詞（`matchPattern` ではなく `matchesPattern`）。

形ごとの詳しい説明と悪い例は `references/booleans.md` にある。

### 5. 何でも指せる動詞を使わない

`check` / `change` / `process` / `handle` / `manage` / `do` は、実際に何が起きるのかを読み手に推測させる。起きることをそのまま動詞にする。

- `checkPassword` → `verifyPassword` / `isPasswordExpired` / `validatePasswordStrength`
- `changeOrder` → `cancelOrder` / `shipOrder` / `refundOrder`
- `handleFile` → `uploadFile` / `compressFile`

`compare` も、比べた結果が何を意味するのかが読めない。`equals` / `contains` / `isOlderThan` のように、何が真になるのかが名前で分かる形にする。

### 6. 対になる操作には対になる語を使う

片方だけ違う系統の語にすると、どれとどれが対応するのかが読めなくなる。

`add` / `remove`、`insert` / `delete`、`create` / `destroy`、`open` / `close`、`start` / `stop`、`enable` / `disable`、`show` / `hide`、`lock` / `unlock`、`push` / `pop`、`connect` / `disconnect`、`attach` / `detach`、`acquire` / `release`、`encode` / `decode`、`publish` / `subscribe`

### 7. 略さない

1文字だけの名前と、その分野で定着していない略語は使わない。`cnt` が `count` なのか `content` なのか、読み手には判断できない。

例外は、数行で終わるループの変数（`i` など）と、定着した略語（`id` / `url` / `http` / `db` / `json`）。

### 8. 品詞を合わせる

- クラス・型・変数は名詞にし、関数・メソッドは動詞で始める。ただし、引数を別の型に変換する関数は `〜From` / `〜Of`（規則9）とし、名詞で始めてよい。
- インタフェースは、性質を表す形容詞（`Iterable` など）か、役割を表す名詞（`〜Repository` など）にする。
- 配列などのコレクションは複数形、その1要素は単数形にする（`orders` の要素は `order`）。
- コールバックには、呼ばれるタイミングを名前に入れる（`onSubmitted` / `beforeDelete` / `afterLogin`）。

### 9. 変換の関数は、変換の向きに合わせて `From` / `Of` / `to` を選ぶ

変換の関数には2つの向きがある。名前の語の並びと変換の向きが逆になると、何を何に変えるのかを読み違える。

| 変換するもの | 形 | 向き | 例 |
|---|---|---|---|
| 引数を別の型に変換する | `〜From`（ConvertFrom の省略）、`〜Of`（ValueOf の省略） | 変換後 ← 引数 | `Date.from(text)` / `Integer.of(value)` / `barFrom(foo)` |
| 自分自身（レシーバ）を別の型に変換する | `to〜`（ConvertTo の省略） | 自身 → 変換後 | `bar.toString()` |

`From` は既存のデータを元に別の型を作るとき、`Of` は値そのものを別の型として読み替えるときに使う。

引数を変換する関数に `to〜` を付けない。`to` は「→ 変換後」と読めるが、変換元の引数は名前の右側に来るため、向きが逆に見える。

```ts
// 「→ Bar」と読めるが、変換元の foo は右側にあり、向きが逆に見える
const toBar = (foo: Foo): Bar => { /* … */ }

// 「Bar ← foo」の順に読める
const barFrom = (foo: Foo): Bar => { /* … */ }
```

**例外:** `map` などに関数を参照として渡すことを意図する関数は、`to〜` でよい。remeda の関数（`R.mapValues` など）や `R.pipe` に参照で渡す場合も同じ。参照で渡すと、`to〜` のほうが左から右へ自然に読める。

```ts
// 参照で渡すと文として読めない
fooList.map(barFrom)

// to〜 なら参照で渡しても自然な順で読める
fooList.map(toBar)
R.mapValues(fooById, toBar)
R.pipe(fooById, R.omit(['draft']), R.mapValues(toBar))
```

参照で渡さず、呼び出すだけの関数は `〜From` / `〜Of` にする。

## 書き終えたら確かめること

- [ ] 新しく付けた名前に `get〜` が無い
- [ ] 名前を読むだけで、ファイルやデータベースの読み書き・通信をするかどうかが分かる
- [ ] クラス名・型名が広すぎて、いくつもの関心事の処理が入り込んでいない
- [ ] 真偽値の名前を `if` の条件に入れて、英文として読める
- [ ] `check` / `change` / `data` / `result` / `temp` / `flag` を使っていない
- [ ] 対になる操作に、対になる語を使っている
- [ ] 引数を変換する関数が `〜From` / `〜Of` になっている（`to〜` は、自身の変換か、参照で渡す関数に限る）
- [ ] 略語や1文字の名前を、許される範囲の外で使っていない
- [ ] 複数形・単数形が、実際に入っているものと合っている
- [ ] 同じ意味に別々の語を使い分けていない（`fetch` と `load` を同じ意味で両方使う、など）
